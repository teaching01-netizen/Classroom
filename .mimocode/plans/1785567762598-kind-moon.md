# Plan: Real-time external check-in freshness (active-room sync) + faster QR startup

## Goal

Fix two check-in page performance problems, verified in code:

1. **External QR-scan check-ins appear 1-5 min late.** Root cause: the only session check-in fetcher is the global scraper (active-session cadence initial 5m / min 1m / max 30m, `internal/scraper/policy.go:40-63`). The `RoomManager` QR worker (`internal/service/room_manager.go:508-583`) fetches **only the QR**, never check-ins. Manual teacher toggles are fine (they call `RefreshNow` synchronously, `internal/service/teacher.go:311-313`).
2. **QR code appears slowly.** Root cause: frontend does 3 sequential round-trips (`POST /api/rooms/from-session` → `POST /api/rooms/{id}/start` → `GET /api/rooms/{id}`, `web/src/features/rooms/api/room.queries.ts:30-52`) plus a fixed 2s poll (`room.queries.ts:26`). Backend chain itself is fast (worker first wake 0.5-1.5s + 1s QR-tier acquire).

**User-approved decisions:**
- Full plan, phased execution (freshness first, matching the diagnosis priority order).
- Snapshot reconciliation after detected change: **async `SetDueNow`** (proven scraper path re-fetches and commits a versioned snapshot; one extra Warwick fetch per change, accepted).
- **No instrumentation** in this plan (no new Prometheus metrics / performance marks).

**Guiding rule (from diagnosis):** do NOT increase global scraper frequency. Only sessions with a running QR room get the fast sync loop.

## Phase P1+P2 — Active-room sync loop + CHECKIN_UPDATED delta events (backend)

While a room is `Running`, a per-room goroutine fetches session check-ins every 3-5s, diffs against last-known state, publishes per-student delta events over WebSocket, and on any change triggers async snapshot reconciliation.

### New files
- `internal/domain/events.go` — WS delta payload types:
  ```go
  type CheckinUpdate struct {
      CourseID   string    `json:"course_id,omitempty"` // omitted when unknown
      SessionID  string    `json:"session_id"`
      StudentID  string    `json:"student_id"`
      CheckedIn  bool      `json:"checked_in"`
      ObservedAt time.Time `json:"observed_at"`
  }
  type CheckinsUpdate struct { // batch fallback for large diffs (>8 students in one cycle)
      CourseID   string         `json:"course_id,omitempty"`
      SessionID  string         `json:"session_id"`
      ObservedAt time.Time      `json:"observed_at"`
      Updates    []CheckinUpdate `json:"updates"`
  }
  ```
- `internal/service/session_sync.go` — sync loop + driver interfaces:
  ```go
  type SessionSyncDriver interface {
      FetchSessionCheckins(ctx context.Context, courseID, sessionID string) ([]domain.StudentCheckin, error)
      SessionRef(courseID, sessionID string) domain.TargetRef
      SetDueNow(ctx context.Context, ref domain.TargetRef) error // in serverless, wired impl delegates to RefreshNow
  }
  ```
  Plus `runSessionSyncLoop(ctx, state)` with: cadence 3-5s jittered; after N consecutive unchanged cycles grow toward 10s, reset to base on any change; on `ErrRateLimited`/429 back off to ~30s+ jitter; on `ErrPoolExhausted` skip cycle (do NOT shorten interval); on `ErrAuthExpired` let the source's internal force-refresh retry handle it, else back off; publish via `eventHub.Publish` directly (never via `rm.emit` / never touch room status).

### Modified files
- `internal/service/room_manager.go`:
  - `RoomState` gains: `courseID string`, `checkinMu sync.Mutex`, `lastCheckins map[string]bool`, `syncInterval time.Duration`, `unchangedCycles int`, `lastSetDueAt time.Time`.
  - Add `SetSessionSync(driver SessionSyncDriver)` — nil-safe setter; loop is a no-op when driver is nil (live mode / tests keep compiling).
  - `StartRoom` (`:189-227`): spawn the sync goroutine alongside `runRoomWorker` with the same `ctx`; pass `state.courseID` (gate: only run when `courseID != ""`).
  - Fix `CreateRoom` dedup bug (`:122-142`): when an existing row is returned, also register it in `rm.rooms` (fixes cross-instance `StartRoom` "room not found", `:196-199`).
  - Make QR worker first wake immediate (`runRoomWorker:524` — run first `shouldFetchQR` check before the first `time.After`).
- `internal/warwick/snapshot_source.go`: add `FetchSessionCheckins(ctx, courseID, sessionID)` building the same `ScrapeTarget` and calling the existing `Fetch` (reuses `ClassAttendanceStudentCheckInSearch`, `:522-601`, pagination, auth retry). Make the acquire budget a field so the sync path uses ~1s (scraper keeps 5s) to reduce TierTeacher contention.
- `internal/app/bootstrap.go`: after scheduler construction (`:187`), build the driver and call `rm.SetSessionSync(...)` only when snapshot runtime is enabled. In serverless mode wrap `SetDueNow` to delegate to `scheduler.RefreshNow` (bounded ctx) — background drain does not run serverless (bootstrap `:205-207`).
- `internal/app/bootstrap.go:81`: `NewEventHub(256, 256)` → `NewEventHub(512, 1024)` (delta stream headroom; drops remain non-blocking and `SnapshotCommitted` stays the durable backstop).

### Sync-loop behavior contract
- First successful fetch only **seeds** `lastCheckins` (no deltas published).
- Per changed student: publish `AppEvent{Type: "CHECKIN_UPDATED", Data: domain.CheckinUpdate{...}}`; if >8 students changed in one cycle, publish a single `CheckinsUpdate` batch instead.
- On any change: `SetDueNow(sessionRef)` — throttled to ≥3s per room (idempotent DB write; scheduler picks it up within `PollInterval` 5s, or inline in serverless via RefreshNow).
- Room stop / ctx cancel → loop exits immediately.

## Phase P3 — Combined idempotent endpoint `POST /api/rooms/from-session/start` (backend)

Single backend operation for the QR startup sequence; returns existing QR when available, else `202` with retry hint. Also accepts `course_id` (needed by P1's sync loop and P5's event payload).

### Modified files
- `internal/service/room_manager.go`: add
  ```go
  func (rm *RoomManager) EnsureSessionRoom(ctx context.Context, sessionID, courseID string) (domain.Room, error)
  ```
  Logic: `GetRoom(sessionID)` → if missing `CreateRoom(sessionID, sessionID, nil)` (dedup now registers) → if not `Running`/`Fetching`, `StartRoom` (idempotent) → store `courseID` on `RoomState` → return room.
- `internal/api/routes.go`: register `r.Post("/from-session/start", startSessionRoomHandler(rm))` **before** `/{id}/start` (`:85`); add `startSessionRoomHandler` next to `createRoomFromSessionHandler` (`:399-419`). Body `{session_id, course_id?}`.
  - If room has valid `qr_url` and `expires_at` in the future → `200 {success:true, data: room}`.
  - Else → `202 {success:true, data:{status:"starting", room_id, retry_after_ms:500}}`.
- Keep the old `POST /api/rooms/from-session` handler untouched (compat for legacy stack + existing tests).

## Key design constraints (findings from design review)

- **EventHub drop risk:** per-student events are low-frequency (≤1 cycle/3-5s/room) but can burst on bulk scan-in → batch (>8 changes) into `CHECKINS_UPDATED`; hub sized 512/1024; `SnapshotCommitted` self-heals any dropped delta.
- **Pool contention:** sync fetches share TierTeacher (2 sessions) with the scraper and toggles → 1s acquire budget for the sync path, skip-on-exhaustion (no interval shortening). Watch `WarwickSessionPoolExhaustedTotal`; raise `WARWICK_TEACHER_SESSIONS` if contended.
- **Serverless:** `SetDueNow` never drains serverless (no background scheduler) → serverless driver's `SetDueNow` delegates to `RefreshNow` (proven in `ToggleCheckin`).
- **Sync loop must not touch room state/status or `rm.emit`** — publish deltas via `eventHub.Publish` directly; auth recovery is the QR worker's job.
- **chi route precedence:** register `/from-session/start` before `/{id}/start`.
- **zod pin:** the frontend api-client relies on a zod v4.4.3 ESM quirk (`data: z.unknown().optional()` passthrough). **Do not upgrade zod** in this work.
- **Multi-instance:** `rm.rooms` is per-process; worst case with 2 instances is duplicate (idempotent) delta events — no corruption. Accept and document; DB room-ownership lease is out of scope.
- **Live mode:** when `SCRAPER_ENABLED=false` the driver is nil and the sync loop no-ops (live reads already hit Warwick).

## Out of scope (explicitly)

- Global scraper frequency changes (diagnosis: increases upstream traffic, worsens QR latency).
- Direct snapshot commit from the sync loop's fetched data (double-fetch elimination) — needs lease/validation integration.
- New dedicated session tier for the sync loop.
- DB `course_id` column / room-ownership lease (multi-instance hardening).
- `SESSION_STATS_UPDATED` emission (counts derivable from the roster cache) and its client UI.
- Instrumentation (per user decision).

## Execution order

P1+P2 (freshness: loop + deltas + hub sizing) → P3 (combined endpoint) → P4 (frontend single-start + polling) → P5 (QR decoupling + WS delta cache writes). Each phase compiles and tests green before the next; backend deploys fully before frontend (old `/from-session` endpoint remains for compat).
